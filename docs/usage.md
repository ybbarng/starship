# 연료 기록 — 토큰 사용량 (`/usage`)

어디에 토큰을 많이 쓰는지 보는 화면이다. 오늘·7일·30일 기간마다 다음을 본다.
- 업무·개인·기타 합계
- 프로젝트 순위, 프로젝트마다 세션 순위
- 날마다 출력량과 모델별 합계

통계는 비서가 아니라 starship이 맡는다(사용자 결정, 2026-11-01). 그래서 starship 서버가 이 컴퓨터의 Claude Code 기록을 직접 읽는다. 기록은 수 GB이고 세션이 쉬지 않고 쓴다. 이 기능이 컴퓨터를 붙잡지 않는 것이 첫째 조건이다(비슷한 도구가 2분마다 기록을 통째로 다시 읽어 CPU 90~100%, 메모리 1.9GB를 쓴 사례가 있었다).

## 데이터

| 무엇 | 어디서 | 뜻 |
|---|---|---|
| 요청 하나(`UsageRecord`) | `~/.claude/projects/<폴더>/<세션>.jsonl`의 `type: "assistant"` 줄 | `message.usage`의 입력·캐시 쓰기(5분/1시간)·캐시 읽기·출력, `message.model`, `timestamp`, `sessionId` |
| 서브에이전트 요청 | `<폴더>/<세션>/subagents/*.jsonl` | 줄의 `sessionId`가 부모 세션이라 그대로 부모에 더해진다 |
| 합계 칸(`UsageBucket`) | 서버가 요청을 읽으며 만든다 | 날·프로젝트·세션·모델마다 요청 수·토큰·처음/마지막 시각. 서버는 요청 하나하나가 아니라 이것만 남긴다 |
| 프로젝트 | 기록 폴더의 작업 경로 | 그 폴더 본 세션 줄의 `cwd` 중 가장 많은 것. 작업 경로가 같은 기록 폴더는 한 프로젝트다(폴더 이름을 바꾸면 기록 폴더가 둘로 나뉜다). 이름만 같으면 부모 폴더를 붙여 나눈다 |
| 영역(업무·개인·기타) | 프로젝트 경로 + `STARSHIP_USAGE_AREAS` 규칙 | 가장 긴 접두사가 이긴다 |
| 추정 비용 | `src/usage/model.ts`의 `PRICES` | API 가격(100만 토큰당 달러). 캐시 쓰기는 입력값의 1.25배(5분)와 2배(1시간), fast 모드는 2배 |

설정(모두 서버 환경 변수):

| 변수 | 뜻 | 예 |
|---|---|---|
| `STARSHIP_USAGE_DIR` | 기록 폴더. 없으면 데모 숫자를 보인다 | `~/.claude/projects` |
| `STARSHIP_USAGE_AREAS` | 영역 규칙. `영역:경로`를 `;`로 잇는다. 영역은 `work`·`personal`·`other` | `work:~/company;personal:~/personal` |
| `STARSHIP_STATE_DIR` | 읽은 위치와 합계를 남길 폴더(기본 `~/.local/state/starship`) | |
| `STARSHIP_USAGE_ACCOUNT_SWITCH` | 계정을 바꾼 날(`YYYY-MM-DD`). 있으면 연료 기록 노트 "계기 읽는 법"에 "그날 앞뒤 기록이 섞여 있다"는 줄을 둔다(`/api/usage`의 `meta.accountSwitch`). 형식이 틀리면 없는 것으로 친다 | `2026-11-01` |

회사 경로는 공개 저장소에 적지 않으려고 코드가 아니라 설정으로 받는다.

## 꼭 지킬 규칙과 보장 방법

| 규칙 | 보장 |
|---|---|
| 기록 전체를 매번 읽지 않는다 | 파일마다 `{ino, offset}`을 기억해 늘어난 부분만 읽는다. 쓰는 중이라 끝나지 않은 마지막 줄은 다음 차례에 이어 읽는다. 파일이 짧아졌거나 inode가 바뀌면 그 파일만 처음부터 읽는다 |
| 저절로 돌지 않는다 | 타이머도 파일 감시도 없다. `/api/usage`가 물을 때만, 그것도 마지막으로 읽은 지 5분이 지났을 때만 읽는다. "다시 읽기"(`?fresh=1`)는 30초. 동시에 온 요청은 한 번 읽기를 같이 기다린다 |
| 줄 하나 때문에 메모리가 늘지 않는다 | 1MB씩 읽고 줄마다 세 창만 본다: 앞 2KB(`model`·`id`), `"usage":{`부터 4KB(usage 객체), 끝 4KB(`type`·`timestamp`·`cwd`·`sessionId`). `"usage":{`가 없는 줄은 글자로 바꾸지 않는다. 1MB를 넘는 줄(수 MB짜리 도구 결과)도 세 창만 복사해 둔다 |
| 첫 읽기도 CPU를 다 쓰지 않는다 | 25ms 넘게 붙잡으면 그만큼 쉰다(코어 하나의 절반쯤) |
| 진짜 usage를 읽는다 | JSON 글 안의 따옴표는 늘 `\"`라서 줄 원문의 `"usage":{`는 진짜 키에서만 나온다. 그래서 첫 번째 것을 쓴다. API 오류 줄은 `type`·`timestamp`가 `message` 앞에 와서 앞 창에서도 찾는다 |
| 한 요청을 한 번만 센다 | 같은 요청이 붙은 여러 줄로 남는다. 최근 요청 5천 개의 값을 기억해, 다음 줄이 오면 앞 값을 빼고 새 값을 더한다 |
| 복사한 기록을 두 번 세지 않는다 | 기록 파일을 손으로 복사·이동하면 같은 요청이 두 파일에 있게 된다(이 저장소를 만든 사람의 경우 프로젝트 폴더 이름을 바꾸며 기록을 새 폴더로 복사해 이어 열었더니 한 파일 6천 개 중 5.6천 개가 겹쳤다). 32일 안에 센 요청 id를 날짜와 함께 기억해 다시 오면 건너뛴다 |
| 서브에이전트를 다른 프로젝트로 세지 않는다 | `subagents/` 아래도 읽고, 프로젝트는 줄의 `cwd`가 아니라 파일이 놓인 폴더로 정한다(worktree 서브에이전트는 `cwd`가 `…/.claude/worktrees/agent-…`). 프로젝트 경로를 정할 때 서브에이전트 줄은 빼고 센다 |
| 앱을 다시 띄워도 처음부터 읽지 않는다 | 새로 읽은 것이 있을 때만 읽은 위치·합계·id를 `usage-cache.json`에 남긴다(임시 파일에 쓰고 이름 바꾸기) |
| 오래된 것은 버린다 | 32일보다 오래 고치지 않은 파일은 열지 않고, 32일보다 오래된 합계 칸과 id는 지운다 |
| 비서 정기 작업을 두 번 세지 않는다 | 정기 작업(`claude -p`)도 `~/.claude/projects`에 기록이 남는다(비서의 상태 폴더 아래에서 돈 작업이면 그 폴더 이름의 기록 폴더). `runs/`의 `total_cost_usd`는 읽지 않는다 |

시험은 두 파일에 있다.
- `src/usage/model.test.ts`: 실제 줄 차례로 줄 읽기(본문 속 가짜 usage, 긴 본문, 오류 줄), 규칙, 가격, 합계 칸, 묶기
- `src/server/usage.test.ts`: 임시 폴더에서 다음을 본다
  - 이어 읽기
  - 1MB 넘는 줄
  - 경계에 걸친 표지
  - 붙은 중복
  - 손으로 복사한 기록
  - 서브에이전트
  - 캐시
  - 다시 쓰인 파일

## 사람과 AI가 어떻게 찾아 쓰나

- 사람: 홈의 "연료 기록", 조종석 승무원판 머리의 "연료 기록 →". 프로젝트 이름이 승무원 id와 같으면 줄에 "선실" 링크가 붙는다. 줄을 누르면 세션이 펼쳐진다.
- AI·스크립트: `GET /api/usage?range=today|7d|30d[&fresh=1]`. 응답은 `UsageResponse`(`src/usage/model.ts`)이고, `meta`에 출처(demo·local), 마지막으로 읽은 때, 걸린 시간이 있다.

## 정확도 한계(화면에도 적는다)

- 토큰 수는 API 응답값이라 정확하다.
- 캐시 읽기가 출력의 수백 배다. 그래서 네 가지(입력·캐시 쓰기·캐시 읽기·출력)를 더하지 않고 나눠 보인다.
- 추정 비용은 API 가격 기준이다. 구독 사용 한도(%)와 1:1로 맞지 않는다(한도 계산식은 공개되지 않았다). 200K가 넘는 긴 문맥 가격처럼 요청마다 달라지는 값은 반영하지 않는다.
- 이 컴퓨터 기록만 센다. 지운 세션, 웹·다른 기기에서 쓴 것은 빠진다. 계정을 바꿔 썼다면 전후 기록이 같은 폴더에 섞이고, 기록에는 계정을 나눌 값이 없다. 바꾼 날을 `STARSHIP_USAGE_ACCOUNT_SWITCH`로 알려 주면 노트에 그 사실을 적는다.
- 기간은 이 컴퓨터 시간대의 자정을 기준으로 한다. "7일"은 오늘을 포함한 7일이라, 지금부터 꼭 168시간 전과는 다르다.
- 화면은 최대 5분 늦다("다시 읽기"로 당길 수 있다).

## 요구사항이 바뀌면

- 계정별로 나누려면 기록에 계정 값이 생겨야 한다. 그 전에는 날짜로 끊는 정도만 할 수 있다. 지금은 바꾼 날을 설정(`STARSHIP_USAGE_ACCOUNT_SWITCH`)으로 받아 알리기만 하고, 합계를 끊지는 않는다.
- 가격이 바뀌면 `PRICES`만 고친다. 합계 칸에 토큰과 모델이 있어 비용은 늘 다시 셈한다.
- 기간을 늘리려면(90일 등) `KEEP_MS`와 `rangeStart`를 고친다. 합계 칸과 id 기억이 그만큼 커진다(30일에 상태 파일 4.6MB).
- 시간 단위 그래프가 필요하면 합계 칸의 날을 시간으로 바꾼다(칸 수가 24배까지 는다).
- 다른 기계의 기록까지 모으려면 그 기계에서 같은 합계 칸을 받아 더해야 한다. 이때 같은 요청이 두 기계에 있으면 두 번 센다.

## 다른 방법과 고른 이유

- **비서가 모아 프로토콜로 주기**: 비서 쪽 일이 늘고, 프로토콜(`starship/1`)에 사용량 모양을 더해야 한다. 사용자가 starship이 맡으라고 정했고, 같은 컴퓨터라 직접 읽을 수 있다.
- **jq·grep으로 그때그때 전부 읽기**(비서 시험 스크립트): 쉽지만 7일에 수십 초가 걸리고 매번 수 GB를 읽는다.
- **요청 하나하나를 남기기**(첫 구현): 30일 6.4만 개라 메모리로는 감당되지만 상태 파일이 17MB였다. 화면은 날 단위 합계만 쓰므로 합계 칸으로 바꿨다.
- **줄 전체를 JSON으로 읽기**(첫 구현): 맞기는 하지만 수십 KB짜리 본문까지 글자로 바꿔 첫 읽기 CPU가 10초를 넘었다. 세 창으로 바꾼 뒤 실제 기록 11.3만 줄에서 전체 JSON 읽기와 결과가 모두 같았다.
- **SQLite에 넣기**: 쿼리가 자유롭지만 의존성과 스키마 이전이 생긴다. 합계 칸 몇천 개는 Map과 JSON 한 장으로 충분하다.

## 연료실 (`/fuel`, 2026-11-01)

연료 기록을 우주선의 한 방으로 그렸다(사용자 요청: "연료실에서 현재 상태·계기를 보고, 연료 기록 노트를 누르면 자세한 도표").

- **연료 계통도**(청사진 유리): 맨 왼쪽은 주 연료통(주간 한도, 아래 "주간 연료"). 금속 원통 탱크 셋(T-1 업무·T-2 개인·T-3 기타)은 들여다보는 창에 오늘 연소 몫만큼 연료가 찬다. 밸브·플랜지가 달린 배관에는 최근 15분 연소가 셀수록 연료 점이 빨리 흐르고, 연소실과 종 모양 노즐의 엔진은 그 영역의 지금 속도만큼 배기 불꽃이 길다. 배관이 엇갈리지 않게 탱크 왼쪽부터 엔진 아래쪽부터 잇는다.
- **계기판**: 아날로그 속도계 넷(전체·업무·개인·기타)과 호박색 숫자판(오늘 연소·연료비·재순환). 지금 속도 = 최근 15분 동안의 분당 출력 토큰(`burn`, 영역 합). 세션 하나는 수백, 여럿이 바쁘면 수천이라 눈금은 로그(바늘 끝 분당 2만). 서버의 최근 요청 기억(`recent`, 마지막 5천 개)으로 셈해서 읽기 간격만큼(최대 5분) 늦을 수 있다.
- **속도 기록**: 오늘 시간마다 평균 분당 출력(시간 합 ÷ 60)을 영역별로 쌓는다. 합계 칸이 시간 단위(`hour`)라 가능하다.
- **연료 기록 노트**: 누르면 자세한 도표(`/usage`, 이름을 "연료 기록 노트"로 바꿈).
- **들어가는 길**: 조종석 계기판 오른쪽 칸(교신 수신과 항법 사이)의 연료·속도 계기(작은 속도계, 엔진별 막대, 오늘 연소), 갑판 단면 기관실의 "연료실 ▸" 문.
- 2026-11-01 사용자 "연료실 좀 못생겼는데, 진지한 느낌으로" 피드백으로 조종석과 같은 재질의 계통도·계기판으로 다시 그렸다.
- 이름마다 마우스를 올리면 실제 뜻이 보인다(탱크 = 그 영역 세션이 오늘 쓴 출력 토큰 등).

## 주간 연료 — 계정 사용 한도 (2026-11-03)

사용자 요청: "연료통 부분에 주간 사용량 전체와 남은 양을 리셋 시간과 함께. 주간 사용량을 나눠서 각 연료통이 쓰는 느낌으로". 탱크 셋(업무·개인·기타)이 주간 한도라는 큰 통 하나에서 나눠 쓴다는 그림이다.

- **값**: 본부의 `GET {base}/v1/usage/limits`(형식은 [`protocol.md`](protocol.md)). Starship은 `/api/v1/usage/limits`로 중계하고(데모는 주간 50%·5시간 30%를 지어낸다), 화면은 1분마다 묻는다(`useUsageLimits`, `src/data/limits.ts`). 본부가 없거나 404면 칸을 숨긴다.
- **연료실(`/fuel`)**: 연료 계통도 한 판에서 왼쪽부터 **주 연료통(T-0) → 급유관 → 탱크 셋 → 연료관 → 엔진 셋**이 한 흐름으로 이어진다(`src/ui/usage/MainTank.tsx`). 주 연료통은 탱크와 같은 금속 원통 말로, 키가 조금 더 크다. 들여다보는 창에는 남은 양만 한 가지 색(옅은 호박색)으로 찬다. 뚜껑에서 나가는 급유관 셋은 엇갈리지 않게 먼 탱크일수록 높이 지나 각 탱크 뚜껑으로 내려앉고, 굵기와 흐르는 점의 밝기가 그 영역이 나눠 쓴 몫(`feedShares`)을 따른다. 탱크 이름판 둘째 줄에 "18.9만 · 오늘 55%"(오늘 세 영역이 태운 연료 중 이 영역 몫), 셋째 줄에 "주간 몫 28%"(주간 한도에서 이 영역이 쓴 몫, 근사). 기준이 다른 두 %가 나란히 있어 낱말("오늘"·"주간 몫")을 붙이고, 뜻은 탱크 말풍선에 적는다(2026-11-03). 주 연료통 이름판은 "주간 50% 남음 · 리셋 수 02:00(6시간 뒤)"(`resetShort`), 5시간 한도가 있으면 둘째 줄. 근사라는 설명과 다른 한도는 말풍선에 둔다. 한도 값이 없으면(본부 없음·404) 주 연료통과 급유관을 그리지 않고 탱크부터 시작한다. 판은 SVG 하나라 좁은 화면에서는 통째로 작아진다(가로 스크롤 없음).
- 2026-11-03 사용자 "주간 연료통이 못생겼는데. 주간 연료통 - 개별 연료통 - 개별 로켓 이렇게 이어져 있는 게 더 나을 것 같아"로, 따로 떨어진 MAIN TANK 판(빗금 층, 점선 이름판, 옆 글)을 계통도 안으로 옮겼다.
- **연료 기록 노트(`/usage`)**: 위쪽에 가로 띠. 쓴 부분을 영역 색으로 나눠 칠한다.
- **조종석 연료 계기**: 작은 줄 "주간 50% · 리셋 7시간 뒤"(5시간 한도가 오면 둘째 줄). 말풍선에 자세히. 80% 넘으면 주황, 95% 넘으면 빨강.
- **시각**: 리셋 시각은 브라우저 시간대(Intl, `ko-KR`)로 적는다. "n시간 뒤"는 1분 시계로 고친다.
- **오래된 값**: 본부 값은 세션이 화면을 바꿀 때만 바뀐다. `at`이 30분보다 오래되면 흐리게 하고 "n분 전 값"을 적는다. 리셋 시각이 지난 한도는 보이지 않고, 남은 한도가 없으면 "리셋됨 · 새 값 기다리는 중".
- **본부가 잠깐 실패할 때**: Starship 서버가 마지막 성공값을 기억해 두었다가 `stale: true`로 준다(`keepLastGood`). 띠·주 연료통이 사라지지 않고 흐려지며 "본부에 닿지 않아 마지막으로 받은 값"이라고 적는다. 받은 적이 없거나 404면 예전처럼 숨긴다.
- **사용량을 못 읽을 때**: `/api/usage`가 실패하면 연료실은 "계기를 켜는 중…"에 멈추지 않고 오류 줄과 "다시 읽기" 단추를 보인다(연료 기록 노트와 같은 방식).

### 영역 몫은 근사다

- 한도 값에는 영역이 없다. 그래서 쓴 몫(`usedPct`)을 이 컴퓨터 기록의 영역별 비율로 나눈다(`splitUsed`, `src/usage/limits.ts`).
- **비율의 바탕은 추정 비용**이다. 한도는 토큰 수가 아니라 모델·캐시까지 따진 계산량으로 깎인다고 보여서(공개 계산식 없음, 위 "정확도 한계"), 출력 토큰만 보는 것보다 입력·캐시 쓰기·캐시 읽기·모델 가격을 다 넣은 추정 비용이 가깝다. 비용을 셀 수 없으면(가격 모르는 모델뿐) 출력 토큰으로 나눈다.
- **구간**: 리셋 구간은 "리셋 7일 전 ~ 지금"이지만 통계의 "7일" 기간(오늘 포함 7일, 자정 기준)을 그대로 쓴다. 합계 칸이 시간 단위라 정확히 끊을 수는 있지만, 화면이 받는 `UsageResponse`에는 영역별 시간 합이 출력 토큰만 있고 비용이 없다. 리셋이 새벽이면 어긋남은 몇 시간이다. 말풍선에 "근사"라고 적는다.
- 웹·다른 기기에서 쓴 것은 기록에 없어 몫에서 빠진다(한도에는 들어간다).

시험: `src/protocol/limits.test.ts`(너그러운 스키마), `src/usage/limits.test.ts`(몫 나누기, 배관 몫 비율, 남은 시간 글, 짧은 리셋 시각, 오래된 값, 데모 값).

다른 방법: 본부가 영역별 몫까지 주게 하기 — 본부도 계정 값만 알아 결국 같은 기록 비율을 써야 하고, 이 기록은 starship이 이미 읽는다.
