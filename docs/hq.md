# 본부 방 — 설계안

본부 방은 비서 세션의 일을 보여 주는 starship 화면이다. 2026-11-12 사용자가 이 방을 만들기로 하고 설계를 starship 세션에 맡겼다. 이 문서는 그 설계안이다. 아래 세 가지는 모두 추천안으로 정해져(2026-11-12) 구현 중이다.

1. **방 모양**: 1안은 비서의 선실(`/crew/secretary`)을 본부 방으로 넓힌다(추천). 2안은 보안 구역처럼 따로 화면(`/hq`)을 둔다. **정함(2026-11-12): 1안, 비서 선실을 넓힌다.**
2. **나르기 기록을 누가 쓰나**: 1안은 비서가 일을 넘길 때 hook이 자동으로 한 줄을 남기고, 비서가 처음 부탁한 세션과 끝을 덧붙인다(추천). 2안은 비서가 도구로 다 쓰고, 3안은 hook만 쓴다. **정함(2026-11-12): 1안, hook + 비서 도구.**
3. **휴대폰에서 나르기가 보이는 범위**: 1안은 맥과 휴대폰 모두 나르기 제목까지 보인다(추천). 2안은 휴대폰에는 건수와 멈춤만, 3안은 맥에서만 보인다. **정함(2026-11-12): 1안, 맥·휴대폰 모두 제목까지.**

각 안의 장단점은 맨 아래 "고른 근거"에 있다.

## 왜 필요한가

본부는 비서 세션이다. 받은편지함과 정기 작업을 챙기고, 세션 사이에 일을 나르고, hook과 비서 대시보드(7787), starship 같은 시설을 고친다. 작업 세션의 선실에는 할 일·지도·브리핑 판이 있어 그 세션이 무엇을 하는지 보인다. 비서의 선실도 있지만 지도가 없어서 할 일 판만 보인다. 비서가 하는 일의 큰 몫인 나르기와 시설 상태는 어디에도 모여 보이지 않는다.

## 방에 둘 것

본부 방은 선실처럼 현황판에 판 넷을 둔다. 순서는 할 일 · 나르기 · 시설 · 지도이고, 들어가면 기다리는 것이 있을 때 "할 일", 없을 때 "나르기"를 먼저 연다.

| 판 | 보이는 것 | 데이터 |
|---|---|---|
| 할 일 | 비서가 나를 기다리는 것(고르기·확인·승인·질문) | 이미 있는 비서 책상. 다른 선실과 같은 부품을 쓴다 |
| 나르기 | 지금 나르는 중인 일. 누가 부탁했고, 지금 어느 세션에 있고, 얼마나 멈춰 있는지 | **새로 만든다**(아래 "나르기 기록") |
| 시설 | 비서 대시보드가 답하는지, 정기 작업마다 마지막 결과, 비서의 자기 점검(doctor), 집·회사 인터넷 연결과 회사 VPN | 이미 있는 스냅숏의 정기 작업 계기(`gauges`)와 연결 상태(`link`) |
| 지도 | 비서 저장소의 시설 고치기 일 | 비서가 지도 파일(`map.json`)을 두면 다른 선실처럼 그린다. 없으면 이 판을 숨긴다 |

시설 판에 새 데이터는 필요 없다. 지금 조종석 여기저기에 흩어진 계기를 한곳에 모은다. starship이 비서에 닿지 못하면 시설 판 맨 위에 "본부에 닿지 못해요"를 보인다. starship 자체가 꺼지면 이 화면도 보이지 않으니, starship 상태는 비서 대시보드가 맡는다.

## 나르기 기록

### 뜻

나르기 하나는 어떤 세션이 부탁한 일을 비서가 다른 세션에 넘기고, 결과를 처음 세션에 돌려주기까지다. 예를 들어 상점 세션이 문서 검토를 부탁하면, 비서가 검토 세션에 넘기고, 검토 세션이 끝내면 결과를 상점 세션에 돌려준다. 여러 세션을 거치면 한 나르기 안에 넘김이 여러 번 생긴다.

나르기 판에서 볼 것은 셋이다. 지금 몇 건이 오가나, 각 건이 어느 세션에 있나, 너무 오래 소식이 없는 건은 무엇인가.

### 형식

나르기에 일이 생길 때마다 기록 파일에 JSON 한 줄을 덧붙인다. 지난 줄은 고치지 않는다. 형식 이름은 `starship-relay/1`이고, 끝의 1은 판 번호다.

```jsonc
{
  "relay": "starship-relay/1",   // 형식 이름과 판
  "id": "R-20261112-0930-a1",    // 나르기 하나의 id. open 때 비서 도구가 시각과 무작위 두 글자로 만든다
  "at": "2026-11-12T09:30:00+09:00", // 이 줄을 쓴 시각
  "kind": "open",                // 아래 표
  "from": "shop",                // open에만: 처음 부탁한 세션(세션을 연 폴더 이름)
  "to": "doc-review",            // forward에만: 넘겨받은 세션
  "title": "결제 문서 검토",      // open에만: 일의 짧은 이름. 40자 안쪽
  "card": "SHOP-142",            // 관련 카드 번호. 없으면 생략
  "note": "검토 끝, 고칠 곳 2건"   // 짧은 한 줄. 없으면 생략
}
```

| `kind` | 뜻 | 이 줄 뒤 상태 | 지금 있는 곳 |
|---|---|---|---|
| `open` | 비서가 부탁을 받음 | 넘기기 전 | 비서 |
| `forward` | 다른 세션에 넘김 | 진행 중 | `to`의 세션 |
| `update` | 진행 소식 | 진행 중 | 바뀌지 않음 |
| `return` | 결과를 처음 세션에 돌려줌 | 돌려줌 | 처음 부탁한 세션 |
| `close` | 끝 | 끝 | 없음 |
| `cancel` | 그만둠 | 그만둠 | 없음 |

화면은 같은 `id`의 줄을 시각 순으로 모아 나르기 하나로 만들고, 마지막 줄로 상태와 있는 곳을 정한다.

- **멈춤 표시**: 끝나지 않은 나르기에 24시간 동안 새 줄이 없으면 노랗게 표시한다. 24시간은 starship 코드의 상수 하나라 쉽게 바꾼다.
- 끝났거나 그만둔 나르기는 7일 동안 흐리게 보이다가 판에서 빠진다.
- `title`과 `note`에는 일의 짧은 이름만 적는다. PR 제목 원문, 메시지 본문, 문서 내용 같은 자료는 적지 않는다. 날짜가 정해진 후속 일을 비서 알림 목록에 적을 때와 같은 규칙이다.

### 누가 쓰나

비서만 쓴다. 작업 세션은 비서에게 부탁하고 결과를 받을 뿐이고, 나르기 전체를 아는 것은 비서뿐이다. 추천하는 1안은 hook과 비서가 나눠 쓴다.

- **비서가 도구로 쓴다**: `relay open|update|return|close|cancel`이다. 부탁을 받으면 `relay open --from shop --title "결제 문서 검토"`로 나르기를 열고 id를 받는다.
- **hook이 넘김을 빠짐없이 남긴다**: 비서 세션이 다른 세션에 메시지를 보낼 때(`SendMessage`) hook이 `forward` 줄을 쓴다. `to`는 받는 세션이다. 메시지가 어느 나르기에 속하는지는 메시지 첫 줄의 `[R-…]` 표시로 안다. 그래서 비서는 넘길 때 메시지 첫 줄에 id를 붙인다. hook은 메시지 본문을 기록에 옮기지 않는다.
- id 표시가 없는 메시지는 "어느 일인지 모르는 넘김"으로 나르기 판 아래에 따로 모인다. 비서가 나중에 `relay`로 이어 붙이거나 나르기가 아니라고 치운다.

### 저장 위치와 보이는 범위

- 기록은 비서 맥의 `~/.local/state/secretary/relays.jsonl`에 둔다. 주인만 읽고 쓰게 권한을 둔다. 회사 일 이름이 들어갈 수 있어 어느 저장소에도 넣지 않는다. 이 공개 저장소에는 형식과 화면 코드만 들어간다.
- 비서 서버가 `GET /api/relays?limit=200`으로 최근 줄 200개를 내주고, starship은 `/api/v1/relays`로 받아 화면에 넘긴다. 보안 구역의 1Password 기록과 같은 흐름이다. 비서가 이 끝점을 아직 모르면 "본부에 나르기 기록이 아직 없어요"로 보인다.
- 데모 모드에서는 지어낸 기록만 쓴다.

## 꼭 지킬 규칙과 지키는 법

| 규칙 | 지키는 법 |
|---|---|
| 넘긴 일이 기록에서 빠지지 않는다 | hook이 비서의 모든 `SendMessage`에 `forward` 줄을 쓴다. 비서의 기억에 기대지 않는다 |
| 기록은 지우거나 고치지 않는다 | 덧붙이기만 한다. 고칠 일은 새 줄(`update`, `cancel`)로 쓴다 |
| 회사 자료가 밖으로 나가지 않는다 | 기록을 저장소에 넣지 않는다. hook은 메시지 본문을 옮기지 않는다. 비서는 짧은 이름만 적는다 |
| 진짜 기록과 데모를 섞지 않는다 | 보안 구역처럼 응답에 출처(데모인지 비서 기록인지)를 붙이고, 비서 연결 모드에서는 데모를 쓰지 않는다 |
| 틀린 줄 하나가 판 전체를 깨지 않는다 | 줄마다 따로 검사하고, 틀린 줄만 빼서 "형식이 틀려 뺀 기록"에 적는다. 보안 구역과 같은 방식이다 |

## 사람과 AI가 찾는 법

- **사람**: 1안이면 조종석이나 선내에서 비서 승무원을 누르면 본부 방이다. 멈춘 나르기가 있으면 본부 방 맨 위에 건수를 붙인다.
- **비서 세션**: `relay list --open`으로 지금 나르는 일을 본다. 세션을 닫을 때 인계 문서(HANDOFF)에 나르는 일을 따로 적지 않고 이 기록을 가리킨다.
- **작업 세션**: 처음에는 기능을 두지 않는다. 자기가 맡긴 일이 어디 있는지 궁금하면 비서에게 묻는다.

## 바뀌면 어디까지 고치나

- 나르기에 칸이 늘면(예: 급한 정도): 형식에 선택 칸을 더하고 나르기 판만 고친다. 옛 줄은 그 칸이 없을 뿐이다.
- 비서가 아닌 세션도 일을 나르게 되면: `from`·`to`가 세션 이름이라 형식은 그대로고, hook이 보는 세션만 넓힌다.
- 방 모양을 1안에서 2안으로 바꾸면: 나르기·시설 판 부품을 그대로 옮기고 경로만 바꾼다. 데이터 끝점은 같다.
- 시설 판이 계기를 더 보여야 하면: 스냅숏에 계기를 더하는 일이라 비서와 프로토콜 문서([protocol.md](protocol.md))를 함께 고친다.

## 고른 근거

### 1. 방 모양

| 안 | 장점 | 단점 |
|---|---|---|
| **1안: 비서 선실을 넓힌다(추천)** | 조종석·선내에서 들어가는 길이 이미 있다. 할 일 판과 처리 단추를 다른 선실과 같은 부품으로 쓴다 | 비서 선실만 판이 넷이라 선실 코드에 비서용 갈래가 생긴다 |
| 2안: 따로 화면 `/hq` | 본부에 맞춘 배치를 마음대로 짤 수 있다 | 할 일 판이 선실과 겹친다. 들어가는 길을 새로 내야 한다. 같은 정보를 다른 모양으로 다시 만들지 않는다는 화면 원칙([crew-views.md](crew-views.md))에 어긋난다 |

### 2. 나르기 기록을 누가 쓰나

| 안 | 장점 | 단점 |
|---|---|---|
| **1안: hook + 비서 도구(추천)** | 넘긴 사실은 빠짐없이 남고, 처음 부탁한 세션과 끝은 비서가 정확히 적는다 | 만들 것이 둘이다. 비서가 메시지에 id를 빠뜨리면 "어느 일인지 모르는 넘김"이 생긴다 |
| 2안: 비서가 도구로 다 쓴다 | 만들 것이 하나고 기록이 깔끔하다 | 비서가 잊으면 빠진다. 바쁠 때 가장 잘 빠진다 |
| 3안: hook만 쓴다 | 비서가 할 일이 없다 | 어느 메시지가 어느 일에 속하는지, 언제 끝났는지 모른다. 메시지 목록일 뿐이다 |

### 3. 휴대폰에서 나르기가 보이는 범위

| 안 | 장점 | 단점 |
|---|---|---|
| **1안: 맥·휴대폰 모두 제목까지(추천)** | 밖에서도 무엇이 멈췄는지 알고 비서에게 답할 수 있다. 책상·보안 구역과 같은 범위다 | 회사 일 이름이 휴대폰 화면에 보인다 |
| 2안: 휴대폰에는 건수와 멈춤만 | 휴대폰에 회사 일 이름이 나가지 않는다 | 무엇이 멈췄는지 보려면 맥 앞에 가야 한다 |
| 3안: 맥에서만 | 가장 좁다 | 밖에서 비동기로 보고 답하려고 만든 선실의 뜻과 맞지 않는다 |

### 보고 버린 안

- **지도의 교신 표지로 나르기를 그리기**: 지도의 교신 표지는 사람과 이야기할 것이라 뜻이 다르다. 또 나르기는 하루에도 여러 번 생기고 끝나서, 저장소의 지도 파일을 그때마다 커밋하기 어렵다.
- **나르기를 스냅숏에 넣기**: 스냅숏은 몇 초마다 모든 화면이 읽는다. 나르기는 본부 방에서만 보면 되니 끝점을 따로 둔다.

## 만드는 순서(정한 뒤)

1. 비서: 기록 파일, `relay` 도구, `SendMessage` hook, `GET /api/relays`.
2. starship: 나르기 형식(`src/protocol/relay.ts`), 중계(`/api/v1/relays`), 데모 기록, 나르기 판.
3. starship: 시설 판.
4. 1안이면 비서 선실의 판 구성 바꾸기, 2안이면 `/hq` 화면. 화면 역할 문서([crew-views.md](crew-views.md))에 한 줄 더한다.

1과 2·3은 따로 해도 된다. 비서 끝점이 생기기 전에는 나르기 판이 "아직 없어요"로 보인다.
