# 그리는 박자 — 하루 종일 켜 둬도 가볍게

선실은 앱으로 설치해 하루 종일 켜 두는 화면이다. 3D 별 하늘과 CSS 애니메이션 140개 남짓(승무원 캐릭터, 실내 깜빡이, 연료실 불꽃)이 쉬지 않고 1초에 60번 바뀌어서, 창 하나가 CPU 코어 1.5개쯤(Chrome GPU·탭·WindowServer 합계)을 계속 썼다(2026-11-02 비서 측정). 그래서 앱 전체가 한 박자에 맞춰 바뀌게 했다.

코드: [`src/ui/kit/pace.ts`](../src/ui/kit/pace.ts)(규칙·순수 함수), [`src/ui/kit/PaceRoot.tsx`](../src/ui/kit/PaceRoot.tsx)(박자기, `providers.tsx`에 하나), [`src/sky/SpaceView.tsx`](../src/sky/SpaceView.tsx)의 `FramePacer`·`CameraRig`. 시험: [`src/ui/kit/pace.test.ts`](../src/ui/kit/pace.test.ts).

## 규칙

| 상태 | 1초에 바뀌는 횟수 |
|---|---|
| 움직이는 중: 비행·끌기·놓은 뒤 미끄러짐·자리 잡기, 누르기·휠·키 입력 뒤 1.5초 | 화면 새로 고침마다(보통 60) |
| 앱 창을 보는 중(초점 있음), 가만히 | `IDLE_FPS` = 15 |
| 창은 보이지만 다른 앱에서 일하는 중(초점 없음) | `BLUR_FPS` = 6 |
| 창이 안 보임(가려짐·최소화·다른 데스크톱, `document.hidden`) | 0 |

움직임은 모두 시간(`Date.now`, 애니메이션 시각)으로 정해진다. 덜 자주 바꿔도 자리와 속도는 그대로이고 부드러움만 준다. 저절로 도는 하늘은 1초에 화면 12px쯤 움직이므로 15번이면 한 번에 1px 남짓이다.

## 어떻게 맞추나

- **3D 하늘(따로)**: 하늘만은 CSS 박자와 따로 그린다. 앱 창에 초점이 있으면 1초에 `SKY_FPS`=30번(2026-11-02 사용자: 창밖이 움직일 거면 매끄럽게, 15·6번에서는 먼 행성이 도는 게 끊겨 보였다). 초점이 없으면 **장식 움직임을 멈추고** 1초에 `SKY_BLUR_FPS`=1번만 그린다. 장식 움직임(저절로 도는 하늘, 행성 자전, 구름 흐름, 별 반짝임, 태양 표면)은 `src/sky/deco.ts`의 장식 시계를 따르고, 초점이 없으면 1초쯤에 걸쳐 멈췄다가 돌아오면 그 자리에서 다시 움직인다. 멈춘 하늘은 끊겨 보일 일이 없다. 진짜 시간을 따르는 것(궤도 위치, 지구 자전 각도)은 그대로 흐르지만 1초 1번이면 눈에 띄지 않는다. Canvas를 `frameloop="demand"`로 두고, `FramePacer`가 rAF마다 `skyShouldDraw`로 그릴지 정해 `invalidate()`한다. `CameraRig`는 비행·끌기·미끄러짐·자리 잡기 중에 `markBusy`를 불러 매 프레임으로 올린다. 저절로 도는 것만 남으면 쉰다(그때 카메라는 목적 자리에서 기본 거리의 0.4%쯤 뒤처지므로 1%를 경계로 둔다).
- **워프 줄기(2D 캔버스)**: 워프 중에만 매 프레임 그린다. 아닐 때는 한 번만 지우고 1초에 10번 워프인지만 살핀다.
- **CSS 애니메이션**: `stepAnimations`가 처음 본 돌던 애니메이션을 멈추고(`pause`), 박자마다 시각(`currentTime`)만 옮긴다. 앱이 스스로 멈춰 둔 것·끝난 것은 건드리지 않고, 끝이 있는 것은 끝에 닿으면 끝낸다. 읽기는 처음 볼 때 한 번만, 쓰기보다 먼저 한다(쓰고 나서 읽으면 그때마다 스타일 계산이 강제된다). CSS 전환(transition)은 짧고 손으로 일으키는 것이라 그대로 둔다.
- **새로 시작한 애니메이션**: 캐릭터의 짧은 동작(`ActClock`)은 몇 초마다 새 애니메이션을 만든다. 다음 박자를 기다리면 그사이 매 프레임 돌고, 캐릭터가 여럿이라 거의 끊이지 않는다. 그래서 `animationstart`를 받아 그 요소의 애니메이션만 바로 박자에 넣는다.
- **SMIL**(SVG `<animate>`, 연료실 불꽃의 일렁임): 바깥 svg를 `pauseAnimations()`로 멈추고 박자마다 `setCurrentTime()`.
- **박자에서 빼기**: `[data-pace-free]` 안의 애니메이션은 건드리지 않고 제 속도로 둔다. 창밖 이벤트(오징어 등이 지나가는 것)가 그렇다. 몇 분에 한 번 몇 초만 돌아서 가볍고, 끊기면 눈에 띈다(2026-11-02 사용자: 다른 앱에 초점일 때 끊겨 보임).

## 실측(설치한 앱 창, 실제 자료, 2026-11-02 비서)

앱 창은 보이고 초점은 터미널에 둔 상태(20초 CPU 시간 차이): Starship 탭 0.09 + Chrome GPU 0.09 + WindowServer 0.10(다른 창 몫 포함) = **0.28코어**. 고치기 전 같은 셋 합계는 약 1.55코어였다. 앱 몫(탭+GPU)은 0.18로 목표(0.2) 안이다. 앱 창에 초점이 있을 때와 창을 가렸을 때는 아직 재지 못했다.

## 측정(헤드리스 Chrome, 1372×872, 픽셀 밀도 2, 데모 자료)

WindowServer 몫은 빠진 숫자다. 실제 앱 창에서는 비서가 잰다.

| 화면 | 전 | 후: 초점 있음 | 후: 초점 없음 |
|---|---|---|---|
| 홈(조종석) | 0.70코어(GPU 0.36, 탭 0.34) | 0.20~0.26 | 0.16~0.20 |
| 연료실 | 0.26 | 0.17 | 0.06 |

같은 자리에서 여러 번 재면 ±0.04쯤 흔들린다. 홈에 남은 몫은 하늘과 CSS가 대략 반씩이고, 5초마다 새로 받는 상태와 이름표 자리 계산이 조금 더한다.

## 하늘을 늘 30번 그렸을 때 실측(설치한 앱 창, 2026-11-02 비서)

초점이 터미널에 있을 때 Starship 탭 0.34 + Chrome GPU 0.35 + WindowServer 0.40 = **1.11코어**. 15·6번일 때(0.28)의 네 배쯤이었다. 헤드리스 측정(+0.13코어)은 실제 GPU·큰 레티나 화면에서의 장마다 비용을 크게 덜 셌다. 그래서 초점이 없을 때는 장식 움직임을 멈추고 1초 1번만 그리게 바꿨다.

## 초점이 없을 때 하늘을 멈춘 뒤 실측(설치한 앱 창, 2026-11-02 13:45, `top` 5초 간격)

같은 렌더러(81237)를 새로고침 전후로 쟀다. 초점은 터미널.

| | 탭 | Chrome GPU | WindowServer | 합계 |
|---|---|---|---|---|
| 새로고침 전(하늘 늘 30번) | 0.36~0.38 | 0.33~0.36 | 0.46~0.50 | 약 1.15 |
| 새로고침 뒤(하늘 멈춤, 1초 1번) | 0.12~0.14 | 0.09~0.12 | 0.15~0.22(다른 창 몫 포함) | 약 0.40 |

앱 몫(탭+GPU)은 0.70쯤에서 0.23쯤으로 줄어, 15·6번 때(0.18)와 비슷해졌다. 남은 몫은 하늘 밖 CSS 애니메이션(초점 없음 6번)이다.

선실 지도에 걷기·폭죽·말풍선·날씨를 더한 뒤(2026-11-02 16:57, 빌드 16:55:03) 같은 렌더러를 30초 다시 쟀다: 탭 0.07~0.10 + GPU 0.07~0.09 = **앱 몫 약 0.16코어**로 늘지 않았다. 앱 창이 어느 화면(조종석·선실)이었는지, 새 빌드로 새로고침했는지는 확인하지 못했다. 걷기·폭죽은 몇 초만 박자기를 깨우고, 말풍선·z z는 다른 CSS 애니메이션처럼 초점 없을 때 1초 6번이라 늘 드는 몫이 작다.

## 하늘 30번으로 올린 값(헤드리스, 세 번씩)

| | 하늘 15·6번 | 하늘 30번 | 하늘 60번 |
|---|---|---|---|
| 앱 창을 볼 때 | 0.19~0.25 | 0.34~0.38 | 0.32~0.51 |
| 다른 앱을 볼 때 | 0.16~0.20 | 0.28~0.36 | |

하늘 한 장의 비용은 넓이·해상도·HDR이 아니라 장마다 드는 고정 몫이다. 하늘 60번 상태에서 HDR을 끄거나(0.04쯤 줄어듦), 해상도를 1배로 하거나, 흐림 판을 끄거나, 캔버스를 화면에 안 내보내도 측정 흔들림 안이었다. JS는 1초 43ms(4%)로 가볍다. 그래서 "보이는 범위만 그리기"·"다른 창을 볼 때 HDR 끄기"는 하지 않았다.

## 해 봤는데 효과가 없던 것·작던 것(2026-11-02)

- **별 수 줄이기**: 4만 1천 개(8등급까지)를 519개(4등급까지)로 줄여도 같은 조건에서 차이가 측정 흔들림 안이었다(1초 15번 0.27 대 0.29~0.38, 60번 0.50 대 0.51). 별은 점이라 GPU가 한 번에 그린다. 감상 모드와 평소 모드로 별을 나누는 것은 성능 까닭으로는 하지 않는다.
- **숨은 선내 빼기**: 조종석에서 선내(캐릭터 100여 애니메이션)는 `visibility: hidden`으로 숨겨 두기만 해서 애니메이션이 계속 돌았다. `display: none`으로 바꿔 아예 뺐다. 줄어든 몫은 1할 안쪽이었다(15번 0.27 → 0.24, 60번 0.50 → 0.48). 그리지 않는 애니메이션은 원래 크게 비싸지 않았다.
- 남은 몫의 대부분은 **CPU가 매번 하는 준비**다: 행성·카메라·이름표 계산(JavaScript), 보이는 SVG·CSS의 스타일·배치, GPU에 명령을 보내는 Chrome GPU 프로세스, macOS 화면 합성(WindowServer). 그래서 1초에 몇 번 바꾸느냐가 가장 큰 손잡이다.

## 바꿀 때

- 더 가볍게: `BLUR_FPS`를 낮춘다(4면 더 끊겨 보인다). 하늘 픽셀 밀도(`dpr={[1, 2]}`)는 헤드리스 측정에서 차이가 작아 그대로 두었다.
- 새 애니메이션: CSS·SMIL로 만들면 저절로 박자를 따른다. `requestAnimationFrame`으로 직접 돌리는 것은 박자를 따르지 않는다. 계속 도는 것이면 `onPaceTick`에 건다. 손으로 일으켜 잠깐 도는 것은 그대로 둬도 된다.
- 앱 CSS가 `animation-play-state`로 애니메이션을 멈췄다 다시 트는 일이 생기면: 박자기가 이미 멈춰 둔 것은 다시 틀어도 박자기 시각을 따른다. 그런 곳이 생기면 `stepAnimations`가 그 애니메이션을 건너뛰게 표시를 둔다.
